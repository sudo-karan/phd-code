**How a stand is typed today.** The export stage vectorises the stand labels, one polygon per
connected piece of a stand, and gives each polygon the commonest stand type among the pixels of
the type image (`cluster_labels`) it touches, each pixel weighted by its share inside the polygon
(`reduceRegions` with `ee.Reducer.mode()`, `src/fmu/stages/export.py`,
`_build_merged_feature_collection`, step 3). A polygon that touches no typed pixel gets a null
type.

**Where the types come from.** The clustering stage trains k-means on one row per stand: the
stand's means, sampled at one of its pixels inside the habitat mask where no band is missing. It
then applies the trained clusters to every pixel of the habitat-masked image of per-stand means.
A stand's means are the same at each of its pixels, so every typed pixel of a stand carries the
type the fitted clusters give that stand's row. A stand with a row has typed pixels, all of its
row's type; a stand without a row has none.

**Which stands have no row in the fit, and what each gets.** The counts are from the committed
records of the eleven `_r9` runs (`docs/reproducibility/r9_runs/`, the clustering manifests'
summary numbers) and from the demo set's re-merge (`docs/demo/remerge/*.json`, 13 Oct runs,
legacy cache layout).

   data over it. In the `_r9` runs, which segment kept land only, no stand lies outside the mask,

#### The change

- **`src/fmu/stages/export.py`** (Locked), `_build_merged_feature_collection`, step 3: the vote is
  made as before, then a stand with a row in the fit takes that row's type
  (`_take_the_fit_rows_types`). The row types come from one grouped reduction per layer part: the
  type image with the stand label image beside it, the commonest type per stand label
  (`_stand_row_types`). With `clustering.fit_excludes_stands_below_min_area` on, the stands below
  the minimum (from `stand_provenance`, as the clustering stage finds them) are taken out of the
  row types, so they keep the vote (question 2); if the setting is on and there is no
  `stand_provenance`, no stand is retyped, with a warning (`_fit_row_types`). Every piece of a
  stand takes the same type, looked up by `stand_lbl` as the provenance is. The lookup inside
  `ee.Algorithms.If` has a default, because Earth Engine may compute both cases of `If`; the
  default is never chosen. `stands_snic` and `stands_dissolved` are typed as before: the brief
  names stands.
- **Why the stand's own typed pixels and not the row itself.** The clustering stage does not keep
  the trained clusters or record which pixel it drew each row from. Every typed pixel of a stand in
  one piece carries its row's type, so on the analysis grid the type its pixels carry is the row's
  type. (Drawing the row again with the fit's seed, as the k elbow step does, is question 3's
  option (c).)
- **Found on the way: the pieces of one stand are averaged apart.** The clustering stage averages
  the features with `reduceConnectedComponents`, which works on each connected piece, so a stand
  in several pieces can carry a different type on each piece; its row is drawn on one of them. The
  write-up above ("A stand's means are the same at each of its pixels") holds for a stand in one
  piece only. For a stand whose pieces differ, the code takes the commonest type over its typed
  pixels, the row's type unless the row was drawn on a piece of another type (question 3). In the
  eleven `_r9` runs this is one stand, in the 10 km tile (below). The code also departs from the
  vote on a piece with no typed pixel of a stand that has a row elsewhere: that piece was null and
  now takes the stand's type; no `_r9` run has one.
- **Earth Engine, seen live:** a grouped reduction gives a group even to a stand whose pixels are
  all untyped, only without a `mode`; the code drops those groups. Found with a read-only check
